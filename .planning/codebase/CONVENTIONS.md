# Coding Conventions

**Analysis Date:** 2026-02-09

## Naming Patterns

**Files:**
- Use `kebab-case` for file names: not observed (all files are single lowercase words)
- Use single lowercase words for source files: `assets.ts`, `commands.ts`, `manifest.ts`, `mcp.ts`, `platform.ts`, `template.ts`, `unity.ts`, `updater.ts`
- Use `kebab-case` for build scripts: `inject-version.ts`
- Test files use `.test.ts` suffix: `unity.test.ts`, `mcp.test.ts`

**Functions:**
- Use `camelCase` for all functions: `findUnityInstalls()`, `parseUnityVersion()`, `getMcpConfigObject()`
- Prefix boolean-returning functions with `is` or `has`: `isWindows()`, `isMac()`, `isUnity6OrNewer()`, `hasMcpConfig()`, `hasClaudeCommands()`
- Prefix getter functions with `get`: `getUnityHubPath()`, `getHomeDir()`, `getMcpRelayPath()`, `getTemplatePath()`
- Use verb-first for action functions: `createUnityProject()`, `addMcpToManifest()`, `generateMcpConfig()`, `copyCommands()`

**Variables:**
- Use `camelCase` for all variables: `projectPath`, `testDir`, `hubPath`
- Use `UPPER_SNAKE_CASE` for module-level constants: `MCP_SERVER_NAME`, `GITHUB_REPO`, `TEMPLATE_BRANCH`, `SCREENSHOT_CAPTURE_CS`

**Types/Interfaces:**
- Use `PascalCase` for interfaces: `CheckResult`, `McpConfig`, `UnityInstall`, `UnityVersion`, `FileChange`
- Export interfaces that are consumed across modules
- Define interfaces close to the functions that use them

## Code Style

**Formatting:**
- No Prettier or ESLint configured. No auto-formatting tool enforced.
- 2-space indentation throughout
- Single quotes for strings
- Semicolons at end of statements
- Trailing commas in multi-line objects and arrays (inconsistent -- some have them, some do not)

**Linting:**
- No ESLint, Biome, or other linter configured
- TypeScript `strict: true` in `tsconfig.json` serves as the primary code quality gate

**TypeScript Strictness:**
- `tsconfig.json` at `src/tsconfig.json` has `strict: true`
- Target: `ES2022`
- Module system: `NodeNext` (ESM)
- Use `.js` extension in import paths even for `.ts` files (NodeNext resolution requirement)

## Import Organization

**Order:**
1. Node.js built-in modules: `import * as fs from 'fs';`, `import * as path from 'path';`, `import * as os from 'os';`
2. Third-party packages: `import chalk from 'chalk';`, `import inquirer from 'inquirer';`, `import ora from 'ora';`
3. Local modules: `import { findUnityInstalls } from '../utils/unity.js';`

**Import Style:**
- Use namespace imports for Node builtins: `import * as fs from 'fs';` (not `import { readFileSync } from 'fs';`)
- Use named imports for third-party and local modules: `import { Command } from 'commander';`
- Use default imports for packages that export defaults: `import chalk from 'chalk';`

**Path Aliases:**
- None configured. Use relative paths with `.js` extension.

## Error Handling

**Patterns:**
- Use `try/catch` blocks around filesystem and external operations
- Wrap errors in `if (error instanceof Error)` before accessing `.message`
- Use `process.exit(1)` for fatal errors in commands (never throw from top-level command handlers)
- Use `ora` spinner `.fail()` to display error state before exiting
- Silent error swallowing with empty `catch {}` blocks for non-critical operations (e.g., reading config files that may not exist)

**Example pattern from `src/commands/init.ts`:**
```typescript
try {
  await copyTemplateAsync(projectPath);
  createEditorScripts(projectPath);
  spinner.succeed('Claude commands installed');
} catch (error) {
  spinner.fail('Failed to install Claude commands');
  if (error instanceof Error) {
    console.log(chalk.red(`Error: ${error.message}`));
  }
  process.exit(1);
}
```

**Example silent catch from `src/utils/template.ts`:**
```typescript
try {
  if (fs.existsSync(versionPath)) {
    return fs.readFileSync(versionPath, 'utf-8').trim();
  }
} catch {
  // Ignore errors
}
return null;
```

## Logging

**Framework:** `console.log` with `chalk` for colored output

**Patterns:**
- Use `chalk.green()` for success messages with checkmark: `chalk.green('✓ Found existing Unity project')`
- Use `chalk.red()` for errors: `chalk.red('❌ No Unity installations found.')`
- Use `chalk.blue()` for informational banners and headers
- Use `chalk.yellow()` for warnings
- Use `chalk.gray()` for secondary/hint text
- Use `chalk.cyan()` for commands/actions the user should run
- Use `ora` spinner for long-running operations: `ora('Creating Unity project...').start()`
- Spinner transitions: `.start()` -> `.succeed()` / `.fail()` / `.warn()`

## Function Design

**Size:** Functions are generally small (under 50 lines). Larger orchestration functions in `src/commands/init.ts` reach ~160 lines but are step-by-step procedural flows.

**Parameters:**
- Use default parameter values for testability (inject platform, homeDir, etc.)
- Platform-dependent functions accept `platform: NodeJS.Platform = getPlatform()` to allow test overrides without mocking
- Options objects for functions with many optional parameters (see `waitForMcpRelay`)

**Return Values:**
- Return `null` for "not found" cases (e.g., `getCommandsVersion`, `getMcpPackageUrl`)
- Return `boolean` for check/validation functions
- Return `void` for side-effect functions (file writes, process spawns)
- Return `Promise<void>` for async side-effect functions
- Return typed objects for data functions (`UnityInstall[]`, `CheckResult`)

## Module Design

**Exports:**
- Export specific named functions, no default exports
- Export interfaces/types that are used across module boundaries
- Export constants that other modules reference (e.g., `MCP_SERVER_NAME`)
- Keep private/internal functions unexported (e.g., `copyDirectorySync`, `downloadFile`, `checkUnityProject`)

**Barrel Files:**
- Not used. Each module is imported directly by path.

## Platform Handling

**Pattern:** Functions that behave differently per platform accept a `platform` parameter with default `getPlatform()`. This enables testing cross-platform logic on any OS.


**Platform checks:** Use `isMac(platform)` and `isWindows(platform)` helpers from `src/utils/platform.ts`. Throw `Error('Unsupported platform')` for Linux.

## File System Operations

- Use synchronous fs operations (`readFileSync`, `writeFileSync`, `existsSync`, `mkdirSync`) for simple operations
- Use `{ recursive: true }` with `mkdirSync` to ensure parent directories exist
- Skip symlinks explicitly during directory copies for security
- Use `fs.rmSync(dir, { recursive: true, force: true })` for cleanup
